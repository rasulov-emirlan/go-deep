## 1. Mechanism

**Partial failure.** A distributed program can be half-broken: node A works, B is dead, the link A<->C drops 30% of packets, and you often can't tell which. Single-machine programs fail together; distributed ones fail *partially and observably-differently*. That is the root difficulty.

**Failure models** (weakest -> strongest adversary):
- **Crash-stop**: node halts forever. **Crash-recovery**: halts, restarts with durable state (Raft/Paxos assume this; volatile state lost).
- **Omission**: node (or link) drops some sent/received messages - send-omission, receive-omission. The BCM5709 NIC that dropped *inbound but not outbound* packets is receive-omission: node kept sending heartbeats so its hot spare never took over -> 5 h outage until reboot (Bailis & Kingsbury, confirmed in text).
- **Timing/performance**: correct but too slow (GC, swap, disk stall).
- **Byzantine**: arbitrary/malicious behaviour; needs 3f+1 (PBFT). Cloudflare titled its 2020 etcd postmortem "A Byzantine failure in the real world" for a *partially failing switch*, though the fault was really omission/asymmetric connectivity (title from search results; details UNVERIFIED).

**Naive detector: timeout.** "No heartbeat for T => dead." **Why it can't be right:** in an asynchronous network a slow node, a dead node, a dropped packet and a partitioned link look identical (silence). A detector is therefore a *guess* trading **completeness** (every dead node eventually suspected) against **accuracy** (live nodes not suspected). Chandra-Toueg formalization (from memory): even unreliable detectors (eventually perfect, "<>P") suffice for consensus; FLP means a perfect one is impossible without timing assumptions.
- Tuning: small T = fast detection, false positives -> needless failovers/elections (which themselves add load - GitHub's 2012-09-10 incident: Percona Replication Manager couldn't health-check a busy MySQL primary, promoted a cold replica, which slowed, failed *back*... then a Pacemaker segfault caused two simultaneous master elections; confirmed in the post). Large T = slow recovery.

**Heartbeats.** Push (node sends "I'm alive" every I) or pull (monitor pings). Fixed timeout T typically 3-10x I. Weakness: needs a hand-tuned T for every network condition.

**Phi-accrual failure detector** (Hayashibara et al. 2004). Instead of a boolean, output a suspicion level phi that grows with time since the last heartbeat, calibrated to the *observed* distribution of inter-arrival times (sliding window). phi = -log10(P(a heartbeat still arrives later than now)). Threshold phi=1 -> ~10% chance of error, 2 -> 1%, 8 -> 1e-8 (from memory). Apps pick their own threshold.
- Akka cluster defaults (reference.conf, confirmed): `threshold = 8.0`, `max-sample-size = 1000`, `min-std-deviation = 100 ms`, `acceptable-heartbeat-pause = 3 s`, heartbeat-interval 1 s; comment: triggers "around 5.5 seconds with default settings". Uses a **normal** distribution.
- Cassandra (`phi_convict_threshold: 8`, cassandra.yaml, confirmed): implementation differs from the paper - it uses an **exponential** distribution, `phi = t / mean * (1/ln 10)` (FailureDetector.java:586, PHI_FACTOR 0.434), sample window 1000; so phi=8 means silence of ~18.4x the mean inter-arrival (computed). Docs: "most users should never need to adjust this"; cloud/high-jitter networks often raise to 10-12 (from memory).

**SWIM** (Das, Gupta, Motivala 2002; from memory + Serf docs confirmed): scalable membership. Separates *failure detection* from *dissemination*.
1. Each period, node picks a random member and **pings** it directly. 2. No ack within probe timeout -> asks **k random members to ping-req** (indirect probe) - tests whether *our* path is bad rather than the target. 3. If nobody gets an ack -> mark **suspect** (not dead) and gossip that. 4. Suspect has a **suspicion timeout** to refute: the suspect (or anyone) can reply "alive" with a higher **incarnation number**; only its owner increments its own incarnation, so a refutation beats older suspect messages. Otherwise -> **dead** (confirm), gossiped. 5. Membership updates are **piggybacked** on ping/ack messages (infection-style), each retransmitted O(log N) times. Per-node load constant regardless of N; detection time bounded expectation, independent of cluster size (paper claim).
- Message precedence (memberlist, from memory): Alive(inc n) overrides Suspect(inc <= n-1..); Suspect(inc n) overrides Alive(inc n) or lower; Dead overrides same/lower incarnation; a node must bump incarnation above the suspect's to refute.
- **memberlist / Serf (HashiCorp)** defaults, `DefaultLANConfig` (memberlist config.go, HEAD 2026-09-29, confirmed): `ProbeInterval 1 s`, `ProbeTimeout 500 ms`, `IndirectChecks 3`, `GossipNodes 3`, `GossipInterval 200 ms`, `PushPullInterval 30 s` (full TCP state sync), `SuspicionMult 4`, `SuspicionMaxTimeoutMult 6`, `RetransmitMult 4`, `AwarenessMaxMultiplier 8`, `GossipToTheDeadTime 30 s`, `TCPTimeout 10 s`. WAN config: probe 5 s / timeout 3 s / suspicion mult 6 / push-pull 60 s. Suspicion timeout = `SuspicionMult * max(1, log10(N)) * ProbeInterval` (util.go:65): computed here N=3..10 -> 4 s, 100 -> 8 s, 1000 -> 12 s, 10 000 -> 16 s; "max" timeout = 6x that (24 s..96 s) - starts at max and **shrinks logarithmically as independent suspicions confirm** (Lifeguard). Note the code comment says `4 * log(N+1)` but the implementation uses log10.
- memberlist also does a **TCP fallback ping** in parallel with indirect probes (state.go ~450-496) - catches "UDP blocked but TCP OK" misconfiguration.
- **Lifeguard** (Dadgar, Phillips, Currey 2017; memberlist README confirmed): adds *local health awareness* - a node that is itself slow/CPU-starved (missing its own acks) raises its Local Health Multiplier (up to `AwarenessMaxMultiplier` 8) and backs off probes/timeouts so it doesn't falsely accuse others; plus dogpile-style suspicion timers and buddy system (tell the suspect it is suspected so it can refute fast). Motivation: slow *observer* looks like many dead *targets*.
- Serf modifications vs SWIM (docs, confirmed): periodic full TCP state sync; separate faster gossip layer (e.g. 200 ms) vs slower failure detection (1 s); dead-node state retained so full syncs propagate it. Consul's LAN/WAN pools = Serf over memberlist.

**Gray failure** (Huang et al., HotOS 2017; definition from search summary): component is "up" to the system's own health checks but degraded for real applications - *differential observability*: observer says healthy, app says unhealthy. Examples: packet loss on one path, flaky disk, thread pool exhausted while /health returns 200, high tail latency. Why detectors miss it: they probe a shallow path (ping) not the app path. Mitigation: probe the real path (deep health checks, request-level success rate), multiple observers' votes, outlier ejection (Envoy), Lifeguard-style awareness.

**Network partitions - types.**
- **Complete**: two components can't talk (classic). **Partial (non-transitive)**: A<->B ok, B<->C ok, A<->C broken. **Simplex/asymmetric**: A->B works, B->A doesn't (receive-omission NIC). (Terminology from Alquraan et al. OSDI'18 "An Analysis of Network-Partitioning Failures in Cloud Systems": complete, partial, simplex - from memory, UNVERIFIED.)
- **What breaks in leader-based systems under partial/asymmetric partitions**: (a) Raft node that can send but not receive keeps timing out & bumping term -> forces leader to step down when its RequestVotes get through (Pre-Vote/CheckQuorum mitigate but introduce their own liveness cases); (b) leader can reach a quorum but not one follower that can reach the others -> that follower campaigns forever, others in "lease" refuse votes (leader stickiness) -> can produce leaderless/flapping states; (c) leader can't reach its followers but clients can reach the leader -> leader steps down (CheckQuorum) though it "looks up" to clients; (d) Cloudflare 2020-11-02: partially failing switch left etcd unable to keep a stable leader for ~6 h (UNVERIFIED details).
- **Split-brain**: two nodes both believe they're primary and accept writes. Causes: false-positive failover + old primary still alive (GC pause, partition), 2-node clusters (no majority possible), Elasticsearch `minimum_master_nodes` too low (Bailis: two simultaneous primaries), DRBD dual-primary, EC2 MongoDB primary isolated (two hours of write loss, `w=safe` not `w=majority`) - all in the post. Cure: majority quorum (odd sizes / witness), **fencing**, epoch/term numbers checked by storage.
- **STONITH / node fencing** ("shoot the other node in the head"): before promoting the standby, make *certain* the old primary can't write: power off via IPMI/iLO/PDU, cut SAN access, revoke cloud API instance. Fencing is required precisely because you cannot know whether "dead" is dead. Risk (GitHub 2012-12-22, confirmed in post): a 90 s network partition (MLAG/spanning tree reconvergence) made Pacemaker+DRBD fileserver pairs declare each other dead and each issue STONITH; delayed delivery meant both were "active", then both shot each other -> both dead, 5 h recovery.
- Resource fencing alternatives: fencing tokens/epochs at the storage (see dist-locks.md), SCSI-3 persistent reservations, lease-based self-fencing (primary must stop serving before its lease expires; Kubernetes leader election `RenewDeadline`).

**"The Network is Reliable"** (Bailis & Kingsbury, ACM Queue 12(7), July 2014 / CACM Sept 2014; full text confirmed via aphyr/partitions-post): first fallacy of Deutsch's list; an informal survey of real outages. Data points (all from the text):
- Microsoft datacenter study (SIGCOMM'11, Toronto+MSR): avg **5.2 devices and 40.8 links failing per day**, median repair ~5 min (max 1 week), median 59 000 packets lost per failure; network redundancy improves median traffic by only **43%**.
- HP managed networks: connectivity tickets = 11.4% of tickets; median 2 h 45 min (highest priority) / 4 h 18 min (all).
- Google Chubby: 61 outages in 700 days; of nine >30 s, four from network maintenance, two "suspected network connectivity problems".
- Jeff Dean, typical first year of a new Google cluster: 5 racks "wonky" (40-80 machines, 50% packet loss), 8 network maintenances (4 may cause ~30 min connectivity loss), 3 router failures.
- GitHub 2012-09-10 (Pacemaker/MySQL, see above); 2012-12-22 (MLAG/STONITH, 90 s partition); a bridge-loop/aggregation-switch incident with 18 min downtime; Fog Creek 2011 (both redundant ToR switches lost power) and 2012 (BPDU flood, 2 h); Cloudflare 2013 Flowspec rule crashed every edge router (1 h); EC2 MongoDB primary isolation (2 h write loss); a 100-200 node company saw 5 distinct partition periods in 90 days at one hosting provider; BCM5709 inbound-drop NIC bug.
- Point of the article: partitions occur at *every layer* (NIC firmware, switches, GC pauses, overloaded processes) - "not all partitions originate in the physical network".

**Kubernetes node lifecycle as a concrete detector (defaults from source, HEAD 2026-09-29).**
- kubelet posts node status every `nodeStatusUpdateFrequency = 10 s` and renews a **Lease** in `kube-node-lease` with duration `NodeLeaseDurationSeconds = 40` renewed every 25% of it = **10 s** (kubelet defaults.go:149-150, kubelet.go:238). Lease heartbeat is a cheap object update instead of a big Node status.
- kube-controller-manager node lifecycle controller: checks every `--node-monitor-period` **5 s**; if no health signal for `--node-monitor-grace-period` = **50 s** (defaults.go; older docs/versions: 40 s) it sets `Ready=Unknown`. Source comment: grace period must exceed HTTP/2 ping timeout (30 s) + read-idle timeout (15 s) and be N x the update frequency.
- Then taints `node.kubernetes.io/unreachable` / `not-ready` (NoExecute). Pods get an auto-added toleration `tolerationSeconds=300` -> **eviction ~5 min** after the taint (docs: "Pods remain bound to Nodes for 5 minutes"); DaemonSet pods have no tolerationSeconds (never evicted). Total worst-case before pods are rescheduled: up to ~50 s + 300 s ~ 6 min. Docs also say "By default, the node controller waits 5 minutes between marking the node as Unknown and submitting the first eviction request".
- **Eviction rate limit**: `--node-eviction-rate` 0.1/s (one node per 10 s); if >= `--unhealthy-zone-threshold` 0.55 of a zone is unhealthy, rate drops to `--secondary-node-eviction-rate` 0.01/s, or evictions stop entirely if the cluster is small (<= `--large-cluster-size-threshold` 50); if *all* zones are unhealthy it assumes control-plane connectivity problem and does not evict. This is partition-awareness: "many nodes silent at once" is more likely *me* than *them*.
- A deleted-but-running pod after partition: StatefulSet requires the old pod be confirmed gone (force-delete or node removal) before recreating - k8s prefers **at-most-one** over availability for StatefulSets (from memory, UNVERIFIED here).
- Leader election Lease for controllers: 15 s / 10 s / 2 s (see dist-locks.md).

## 2. Edge cases & gotchas
- **Slow != dead**; GC/VM pause/disk stall > timeout produces false suspicion. Why: silence is silence. Fix: adaptive detectors (phi), awareness (Lifeguard), confirm via indirect probes.
- **Observer-side slowness**: a CPU-starved monitor declares healthy targets dead. Why: it's *its* clock/scheduler. Fix: Lifeguard LHM, multiple confirmers.
- **Heartbeat path != work path**: heartbeat thread alive while worker threads deadlocked/queue full (gray failure). Why: shallow probe.
- **One-way link failures** keep keepalive flowing in one direction only (BCM5709). Why: heartbeats sent != heartbeats received. Fix: bidirectional/request-response health checks.
- **Suspicion timeout scales with log10(N)** in memberlist (4 s @10 nodes, 12 s @1000): larger clusters detect slower. Why: more time for refutation/confirmation to spread.
- **Incarnation numbers reset** if a node restarts without persisting them -> stale "dead" gossip can outrank fresh "alive"; memberlist rejoin protocol/`skipIncarnation` handles (code: `nextIncarnation`, `skipIncarnation`, state.go:808-814). Serf keeps dead state for a while (so a returning node hears it was declared dead and refutes).
- **Gossip convergence is probabilistic**: O(log N) rounds, fanout 3 every 200 ms; partitions heal by periodic push/pull TCP sync (30 s).
- **Two-node clusters can't resolve a partition** (DRBD dual-primary, NetWare): no majority. Need witness/quorum device.
- **Failure-detector-driven failover storms**: mass false positives (e.g., after network blip) trigger simultaneous rebalancing; k8s rate-limits evictions per zone; Cassandra/Akka use hysteresis.
- **STONITH with delayed messages** can kill both nodes (GitHub 2012). Also: fencing device (IPMI) may be on the same failed network.
- **Clock-based leases + GC**: see dist-locks.md.
- **Partition healing is where damage shows**: old primary returns and rolls back everything on the new one (MongoDB EC2 case, 2 h of lost writes) -> require majority write concern / consensus.
- **TCP won't tell you**: a dead peer with no traffic isn't noticed for hours by default (keepalive default 7200 s on Linux, `tcp_keepalive_time`; verify with networking notes) - use app-level heartbeats or `TCP_USER_TIMEOUT`/`SetKeepAlivePeriod`.
- **Kubernetes**: node `NotReady` != pods dead; pods keep running on a partitioned node, then double-run when rescheduled after the 5 min toleration -> apps with singleton semantics still need fencing.
- **Readiness/liveness probes are failure detectors too**: liveness checking dependencies restarts everything in a loop (see existing bank answer).

## 3. Common misconceptions
- "We can detect failures reliably with a heartbeat" - only probabilistically; impossible in async nets.
- "CAP says pick two of three" - partitions aren't optional; choice is C vs A *during* a partition.
- "Partitions are rare / cloud network is reliable" - Bailis & Kingsbury data above; 5.2 devices/day in one study; redundancy gave only 43% improvement.
- "A partition means the network is totally cut" - most real ones are partial/asymmetric/gray.
- "Quorum prevents split-brain, done" - not with pauses (old primary keeps acting), or with misconfigured `minimum_master_nodes`; need fencing/epochs.
- "SWIM declares a node dead after one missed ping" - direct probe -> indirect probes -> suspect -> timeout -> dead.
- "Phi-accrual is a probability the node is dead" - it's a scaled suspicion on the inter-arrival distribution; threshold is an app choice.
- "Byzantine = anything weird" - it means arbitrary/malicious behaviour; most production faults are crash/omission/timing.
- "Kubernetes evicts pods after 40 s" - no: ~50 s to mark Unknown (or 40 s in older versions) + 5 min toleration.
- "STONITH is always safe" - can double-kill; also requires a reliable out-of-band channel.

## 5. Illustration plan
**Scene A - "Slow or dead?" (7 frames).** 1. Monitor M pings node N every 1 s (ladder diagram, arrows). 2. Ack returns each time. 3. N pauses (GC bar); pings unanswered; timer T counts. 4. T fires: M declares dead - N wakes 50 ms later. 5. **STOP: "Can M ever be sure?"** three lookalike causes: crash / slow / link drop, same silence. 6. Fixed T vs adaptive: histogram of inter-arrival times with phi curve rising. 7. Trade-off slider: fast detect vs false positives.
**Scene B - "SWIM round" (9 frames).** Ring of 8 members. 1. A picks B, ping. 2. No ack in 500 ms. 3. A asks C,D,E: ping-req(B) (indirect). 4. Also TCP fallback ping. 5. No acks -> B = suspect (yellow), gossip piggybacked on pings, fanout arrows. 6. **STOP: refutation** - B alive, bumps incarnation 4->5, broadcasts Alive(5) which beats Suspect(4). 7. Alternative branch: suspicion timeout (4 s x log10 N) expires -> Dead (red), gossip spreads in O(log N) rounds. 8. **STOP: Lifeguard** - A itself is slow (LHM up to 8), probes back off so A doesn't falsely accuse. 9. Push/pull TCP sync heals a partitioned half.
**Scene C - "Partitions and split-brain" (8 frames).** 1. Cluster of 5 with leader L. 2. Complete partition 3|2 (minority sees no heartbeat). 3. Partial partition: A-C link cut, B still sees both (non-transitive triangle). 4. Simplex: node X can send, not receive (BCM5709). 5. **STOP: 2-node cluster with partition -> both promote (split-brain)**, two writers diverge. 6. Quorum fixes: minority side stops. 7. **STOP: old primary paused, not partitioned** - quorum doesn't stop it; add fencing token/STONITH. 8. Heal: divergent writes; rollback of 2 h of writes (MongoDB EC2 anecdote).
**Scene D - "Kubernetes: how long until my pod moves?" (8 frames).** Timeline with real timers. 1. kubelet heartbeat every 10 s (Lease renew; status). 2. Node loses network at t=0. 3. Controller checks every 5 s; grace 50 s counter. 4. t~50 s: Ready=Unknown, taint NoExecute unreachable. 5. Pod tolerationSeconds=300 bar fills. 6. t~350 s: eviction (rate-limited 1 node/10 s; zone threshold 0.55 stops evictions). 7. **STOP: node was only partitioned - old pods still running -> two copies; what protects a StatefulSet / singleton?** 8. DaemonSet exception (never evicted).
