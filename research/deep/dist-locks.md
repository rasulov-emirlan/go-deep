# dist-locks: Distributed locks, leases & fencing

Verification note: martin.kleppmann.com and antirez.com were egress-blocked for WebFetch. The Redis Redlock spec (redis-doc raw markdown), etcd source/docs, ZooKeeper docs/recipes, Postgres SGML docs, Consul and client-go source were read directly. The Kleppmann/antirez debate below is written from memory of the posts and cross-checked only against search-result summaries and etcd's own docs (which cite Kleppmann) -> details marked UNVERIFIED where I could not confirm wording.

## 1. Mechanism

**Naive lock.** `SET lock:x <id> NX PX 30000` (Redis): only-if-absent + TTL so a crashed holder can't deadlock everyone. Release = compare-and-delete via Lua (`if get==id then del`), else you delete someone else's lock (Redlock doc, confirmed).
**Failure of the naive lock (the whole interview):** the TTL is a *guess about how long the holder will run*. The lock service can only observe time; the holder can be paused invisibly:
1. Client A acquires (TTL 30 s). 2. A stalls (stop-the-world GC, VM pause/live migration, SIGSTOP, swap storm, cgroup CPU throttling, slow syscall, packet delayed in the network). 3. TTL expires; B acquires. 4. A wakes, still believes it holds the lock, writes -> **both act as holder**. A "check `time.Now() < expiry` then write" does not help: the pause can occur *between* the check and the write (TOCTOU).
- Clock variants: wall clock jumps (NTP step, admin `date`, VM restore) on the lock server make keys expire early; on the client make it think the lease is longer.
- Async replication variant (Redis master + replica): A locks on master, master dies before replicating, replica promoted, B locks -> two holders (Redlock doc admits this).

**Fix = fencing token** (Kleppmann; Chubby "sequencer"; etcd docs say the same): the lock service returns a **monotonically increasing number** with each grant. The *resource* (storage) remembers the highest token seen and **rejects writes with a lower one**. A's late write carries token 33 < 34 -> rejected. Requirements: (a) service issues strictly increasing tokens, (b) the resource can check them (compare-and-set / conditional write). Mutual exclusion is enforced at the resource, not by the lock.
- Consequence: if the resource can do conditional writes, you often don't need the lock for *correctness* at all (optimistic concurrency / CAS is the real mechanism; the lock just reduces conflicts). etcd docs (learning/why.md) say exactly this: lease "provides an optimization mechanism for reducing a number of aborted requests"; mutual exclusion comes from version-number validation; etcd's lock cannot protect *external* resources unless they do such validation.

**Efficiency vs correctness locks** (Kleppmann's framing, from memory):
- *Efficiency*: lock prevents duplicate work (dedupe a cron, avoid recomputing a cache). Occasional double-holder = wasted money, harmless. Redis single-node `SET NX PX` is fine.
- *Correctness*: double-holder corrupts data / double-charges. Need consensus-backed lock **and** fencing (or don't use a lock; use DB transaction / CAS).

**The Redlock algorithm** (spec from redis-doc, confirmed): N=5 independent masters (no replication). Client: (1) t0 = now; (2) `SET key rand NX PX ttl` on all sequentially with small per-node timeouts (e.g. 5-50 ms for a 10 s TTL); (3) elapsed = now - t0; lock acquired iff >= N/2+1 (3) nodes granted **and** elapsed < TTL; (4) validity = TTL - elapsed (minus clock-drift allowance); (5) on failure unlock *all* nodes. Retry after random delay. Assumes local clocks tick at ~same *rate* (no synchronized clocks). Persistence: fsync=always for crash safety, or "delayed restarts" (restarted instance stays out for >= max TTL). Doc's own guarantee: mutual exclusion "only as long as the client holding the lock terminates its work within the lock validity time".

**Kleppmann's critique** ("How to do distributed locking", 2016-02-08; from memory + search summary):
1. Redlock produces **no fencing token** (random string isn't monotonic), so it cannot protect against the pause scenario, whatever the algorithm's internals.
2. Redlock is built on a **synchronous-system model**: bounded network delay, bounded process pauses, bounded clock error. Real systems violate all three. Example he gives (UNVERIFIED wording): 5 nodes A-E; client 1 locks A,B,C; clock on C jumps forward -> key expires; client 2 locks C,D,E; both hold. Another: a client-side pause/delayed packet after acquiring.
3. Restart without fsync can lose locks. Verdict: "neither fish nor fowl" - too heavy for efficiency locks (5 servers), not safe enough for correctness locks. For correctness use a proper consensus system (ZooKeeper/etcd) **plus** fencing tokens.
**antirez's reply** ("Is Redlock safe?", 2016-02-09; from memory, UNVERIFIED wording; search summaries are unreliable on it): (1) Fencing: a monotonic counter isn't the only way - Redlock's unique random token can be used with a check-and-set / transaction on the resource; and if the resource supports that, you don't need a lock at all (locks are useful precisely when there is *no* CAS on the resource). (2) Clocks: Redlock only requires `gettimeofday`-style clocks with bounded *drift*, not synchronized; use a monotonic clock; a big step by a misconfigured NTP is an operational error the system model excludes. (3) Delays: the client checks elapsed time *after* acquiring (step 3), so delays during acquisition are detected; pauses *after* the check and before using the resource are unavoidable for **any** lock system including ZooKeeper/consensus ones - so this critique is not specific to Redlock. (4) Restarts: covered by delayed restarts/fsync. Net: the two disagree mostly about the *system model* (asynchronous with unbounded pauses vs. partially synchronous with bounded drift) and what "correctness" needs. **Trust**: Kleppmann's conclusion (a lock without a fencing check can't give safety against unbounded pauses) is a logical point nobody refutes; etcd's docs and etcd's `contrib/lock` demo adopt it. antirez's point (2) that this is not unique to Redlock is also right, but consensus-based locks + fencing *do* close the hole while Redlock cannot issue tokens.

**Lease** = lock with a TTL where the *holder must keep renewing*; safety relies on holder and granter agreeing on duration (clock *rate*, not absolute time) - Gray & Cheriton 1989; Redlock doc cites it. The holder must stop acting **before** the granter's expiry (minus margin): holder timer starts at *request send* time, not response receipt.

**Consensus-backed implementations.**
- **etcd**: lease = TTL object (`Grant`, `KeepAlive` stream, `Revoke`); keys attached with `WithLease` are deleted when it expires. Lock (`client/v3/concurrency.Mutex`, confirmed in source): each contender does a txn `if CreateRevision(myKey)==0 then Put(pfx/<leaseID>, WithLease) else Get` and reads the lowest-CreateRevision key under the prefix; lowest = holder; others `waitDeletes` on the predecessor (no herd). `Session` = lease + keepalive; **default session TTL 60 s** (session.go:26); `Session.Done()` closes when keepalive fails. `Mutex.Header().Revision` / `myRev` (CreateRevision) is the **fencing token**: monotonic across the cluster since it's the Raft-ordered revision. etcd clamps small TTLs: minimum lease TTL = `ceil(1.5 * electionTicks * heartbeat)` = 1.5 s with defaults (server.go:344). Client keepalive assumes a first TTL of 5 s (`defaultTTL`), retries after 500 ms (lease.go:81-86). Leases are kept by the leader; checkpointed to Raft every 5 min by default (`defaultLeaseCheckpointInterval`) so a new leader doesn't reset TTLs to full.
- **ZooKeeper**: **ephemeral** znodes tied to a *session*; session lives while heartbeats reach *some* server within the session timeout; negotiated between `minSessionTimeout` (default 2*tickTime) and `maxSessionTimeout` (20*tickTime) (docs, confirmed). Lock recipe (recipes.mdx, confirmed): create `lock-` EPHEMERAL|SEQUENTIAL; `getChildren`; lowest sequence = holder; else `exists` with watch on the *next-lowest* node; unlock = delete own node; handle create-succeeded-but-connection-lost via GUID in node name. **zxid** / the sequence number can serve as fencing token. Session expiry is decided by the leader; a client that is paused learns on reconnect (gets `SESSION_EXPIRED`; `Disconnected` state != expired - client must not assume it lost the lock until Expired... but it may not *know* about expiry while paused: same pause hazard).
- **Consul**: session (TTL, health checks, `lock-delay` default 15 s, max 60 s: session_endpoint.go:32, structs.go:214) + KV `acquire`/`release`; the server multiplies session TTL by 2 (`SessionTTLMultiplier = 2`, structs.go:2954, session_ttl.go comment) to add slack; **lock-delay** prevents re-granting a lock for N s after a session invalidation - a crude guard against the pause scenario (not a fence). `ModifyIndex` can serve as token.
- **Kubernetes Lease / client-go leaderelection**: default LeaseDuration **15 s**, RenewDeadline **10 s**, RetryPeriod **2 s** (component-base defaults.go; kube-controller-manager options test shows 30/15/5 in its own config); requires `RenewDeadline > 1.2 * RetryPeriod` (JitterFactor 1.2). Doc comment: tolerance to clock *skew rate* ~ LeaseDuration/RenewDeadline; "some method of clock synchronization... highly recommended". **It does not fence** - a paused leader can still act; the docs call it alpha and only "best effort" mutual exclusion. Use resourceVersion CAS on writes for safety.
- **Postgres advisory locks** (docs mvcc.sgml "Advisory Locks", confirmed): app-defined, *not enforced by the system*; **session-level** (`pg_advisory_lock`, held until unlock or session end, ignore transaction rollback, stack/re-entrant counts) vs **transaction-level** (`pg_advisory_xact_lock`, auto-released at commit/rollback, no explicit unlock); `pg_try_advisory_lock` non-blocking; live in shared memory bounded by `max_locks_per_transaction * (max_connections + max_prepared_transactions)` ("tens to hundreds of thousands"). Fine for efficiency/single-DB coordination (outbox relay, cron leader). Safety limits: released only when the *server* notices the session ended (dead TCP peer may linger until keepalive/`tcp_user_timeout`); lock state is in shared memory, not replicated -> after failover the new primary has no locks (inference, UNVERIFIED but follows from docs: lock table is shared-memory only); a paused client whose connection survives *still holds it* (good) - the DB is the single arbiter, so the pause hazard shifts to "client writes after its own DB session died". If the write is in the same transaction/connection as the lock (`pg_advisory_xact_lock` + DML), the DB itself fences: connection loss aborts the txn. That is the strongest practical pattern.

**Leader election via lease** = same lock with a long-lived holder: candidates try to create/renew a key with TTL; holder renews at ~TTL/3; on failure to renew by `RenewDeadline` **it must stop leading** (self-fencing). etcd `concurrency.Election` (Campaign/Resign/Observe) uses the same lowest-revision scheme; leader identity = key + revision; downstream writes should carry `leaderRevision`.

## 2. Edge cases & gotchas
- **TTL shorter than worst-case pause -> two holders.** Why: expiry is decided by the granter's clock, action by the holder's, with no coordination. Fix: fencing, not longer TTL.
- **Renewal thread starved / renew RPC hangs**: holder keeps working after lease loss. Why: keepalive and work share CPU/network. Fix: derive the work context from the lease (cancel on `Session.Done()`), set a deadline < TTL.
- **`time.Now()` for lease math**: Go's `time.Since` uses the monotonic clock (safe vs NTP steps) but Linux `CLOCK_MONOTONIC` does **not** advance during system suspend (documented in `clock_gettime(2)`; UNVERIFIED here) -> VM/laptop suspend can make an expired lease look valid. Wall clock steps break comparisons across hosts.
- **Release-by-DEL bug**: unlocking someone else's lock after your own expired. Why: no ownership check. Fix: compare-and-delete with random value (Lua) / txn on CreateRevision.
- **Re-entrancy**: Postgres session locks stack (N locks need N unlocks); etcd Mutex reuses key for same session; Redis SET NX does not.
- **Pooler hazard**: `pg_advisory_lock` (session level) through PgBouncer transaction pooling: lock attaches to a server connection that gets reused by other clients / unlock goes to a different connection -> leaked or foreign lock. Use `_xact_` variants or session pooling. (Consistent with docs semantic; PgBouncer behaviour from memory, UNVERIFIED.)
- **ZooKeeper `Disconnected` vs `Expired`**: on disconnect the client must treat lock as *possibly lost* but session may still be alive server-side; on reconnect within timeout, ephemerals survive.
- **etcd Lock() returns after waitDeletes but re-checks its own key** ("is the session key lost?" -> `ErrSessionExpired`, mutex.go). Why: lease could expire while queued.
- **Herd effect**: naive "everyone watches the lock key" stampedes; recipes watch only predecessor.
- **Lock granularity/contention**: a global lock in a hot path serializes the whole cluster; also lock service (etcd) throughput is low (writes via Raft, fsync) - not a per-request primitive.
- **Redlock with fewer than N independent failure domains** (e.g., 5 Redis on one host/AZ) collapses to single-node safety. Clock drift assumption: MIN_VALIDITY = TTL - (T2-T1) - CLOCK_DRIFT (spec).
- **Kubernetes leader election is not a fence**: two controllers can briefly act after lease loss until renewDeadline logic trips.
- **Lock + non-idempotent side effect** (charge, email): even with fencing, external APIs may not check tokens -> need idempotency keys. Fencing only works if *every* resource checks.

## 3. Common misconceptions
- "Redis `SET NX PX` is a distributed lock, done" - single node = SPOF; replica failover = two holders; TTL pause hazard remains.
- "Redlock is safe because it uses 5 nodes / majority" - majority does nothing for pauses or clock jumps; no fencing token.
- "Redlock is useless" (overcorrection) - fine for efficiency locks; even Kleppmann says so.
- "Use ZooKeeper/etcd and you're safe" - only with fencing; consensus makes the *lock service* consistent, not the client's belief.
- "A longer TTL fixes it" - shifts probability, adds failover latency, never zero.
- "GC pause can't happen in Go" - Go STW pauses are short (my measurement: max STW 303 us with 2 GiB heap churn), but the hazard is any pause: SIGSTOP/VM freeze/CFS throttling/blocking IO, not just GC. Keep the example as "stall", not "Go GC".
- "Check the lease is valid, then write" is atomic - it isn't.
- "Postgres advisory locks are distributed locks" - they're single-DB, non-replicated, session-scoped.
- "Leader election = mutual exclusion" - there can be two *believers* briefly; only fencing/epoch checks give exclusion.

## 4. Go tie-ins
- **Demo run here** (`/tmp/research/dist-locks/main.go`, go1.24.7): a worker takes a 2 s "lease", checks `time.Now().Before(lease)` (true), then parent sends SIGSTOP for 3 s; on SIGCONT the worker's write happens ~6 s after the check, 4.2 s after lease expiry, with the check still "passed". Also: monotonic clock kept counting during SIGSTOP. Second run measured `runtime.MemStats.PauseNs` max = 303 us for 2000x1 MiB alloc + `runtime.GC()`.
- etcd client: `concurrency.NewSession(cli, concurrency.WithTTL(10))`, `m := concurrency.NewMutex(s, "/locks/x")`, `m.Lock(ctx)` (ctx deadline bounds the *wait*, not the hold), `defer m.Unlock(ctx)`. Fencing: `m.Header().Revision` or `m.Key()` CreateRevision -> send with every write; storage does `Txn(If(ModRevision(k) < token))`/reject stale. Watch `s.Done()` to cancel the work context. `contrib/lock` in etcd repo is a runnable Kleppmann demo (client + storage that validates versions).
- `context.WithDeadline(ctx, leaseExpiry.Add(-margin))` for the critical section; still not a fence because pause can occur after the deadline check.
- go-redsync/redsync implements Redlock (listed in Redis doc); `Mutex.Extend`, `Valid()` are best-effort checks.
- client-go: `leaderelection.RunOrDie` + `OnStartedLeading(ctx)` (ctx cancelled when leadership lost) / `OnStoppedLeading`; typical pattern is `os.Exit` on stop.
- pgx: `pg_try_advisory_xact_lock(hashtext($1))` inside `tx`; keep the work in the same tx.
- Deadlock-safe TTL heuristics: TTL >= 3 x renew interval; renew at TTL/3 (k8s uses 15/10/2).

## 6. Existing interview questions
- `databases-redis-use-cases`: says "SET key val NX PX 30000. Redlock is debated, and you need fencing tokens for correctness" - right but thin; doesn't explain why (pause) or the release-Lua rule.
- `databases-consistency-without-transactions`: "Distributed locks with fencing tokens (etcd, ZooKeeper, or a lease in Redis). Without fencing, a paused process can still write after its lock expires." Correct (though "a lease in Redis" can't produce a monotonic token by itself unless you `INCR` a counter separately - which is not atomic with lock grant across failover).
- `concurrency-patterns-stuck-pending-task`: PENDING as lease + `WHERE attempts = $2` compare as fencing token - correct and a good practical example; note `attempts` must be incremented on *every* claim for it to be monotonic per task.
- `messaging-outbox-relay-concurrency`: "advisory lock `pg_try_advisory_lock`, k8s lease" for leader election - right for efficiency; should mention session-level lock + PgBouncer transaction pooling pitfall and that duplicates must still be tolerated (idempotent consumers) since neither is a fence.
- `databases-locks-types`: advisory lock one-liner correct (missing session vs xact levels).
- `architecture-cache-stampede` (NX mention): single-flight/lock for stampede is an *efficiency* lock - consistent.
- Gap: no question on "why is a TTL lock unsafe" or "Kleppmann vs antirez".
