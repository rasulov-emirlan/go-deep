## 1. Mechanism (whiteboard order)

**Naive model:** `connect()` sends SYN, gets SYN-ACK, sends ACK; `accept()` returns a socket. Two kernel queues hide in between.
- **SYN queue** (half-open, state SYN_RECV): filled when SYN arrives, server sends SYN-ACK. Limit `net.ipv4.tcp_max_syn_backlog` (per listener; min 128, scales with RAM; here 1024). ~304 B per request sock.
- **Accept queue** (fully established, waiting for `accept()`): limit `min(listen(backlog), net.core.somaxconn)`. `somaxconn` default **4096 since Linux 5.4 (was 128)** (kernel doc; this container: 4096). Go's `net.Listen` reads `/proc/sys/net/core/somaxconn` and passes that as backlog.
- Third-ACK arrives → request sock moves SYN queue → accept queue. If accept queue is full: by default (`tcp_abort_on_overflow=0`) the kernel **drops** (the ACK, and new SYNs) instead of RST; server keeps retransmitting SYN-ACK. `=1` sends RST (client sees ECONNRESET/refused — kernel doc warns it "can harm clients").
- **SYN cookies** (`tcp_syncookies=1`, default): when SYN queue overflows the server encodes state in the ISN of the SYN-ACK and keeps nothing; state is rebuilt from the returning ACK. Kernel doc: a *fallback* against SYN flood, "MUST NOT be used to help highly loaded servers" — if you see "possible SYN flooding" with legitimate load, tune the backlogs. Cookie loses TCP options (older kernels; timestamps/sack encoded in ts field if timestamps on).

**Connection teardown:** FIN = "I'm done sending" (half-close, orderly); RST = abort, discards buffers, peer gets ECONNRESET. Active closer ends in **TIME_WAIT** for 2×MSL (Linux hard-codes 60 s; `tcp_fin_timeout` is NOT that — it's FIN_WAIT_2 for orphans). Why: (1) if the final ACK is lost the peer retransmits FIN — someone must still be there to re-ACK, not RST; (2) old duplicate segments from the previous incarnation of the 4-tuple must expire so they can't corrupt a new connection. TIME_WAIT lives on the **active closer** (verified: after 5 client-initiated closes on loopback, +5 sockets in state 06 in /proc/net/tcp).

**Throughput mechanics:** slow start (cwnd = initcwnd, **10 segments** = RFC 6928, ≈14.6 KB; doubles per RTT) → congestion avoidance; receiver window (rwnd) = flow control; send rate ≤ min(cwnd, rwnd)/RTT. Loss ⇒ retransmit by RTO (Linux min RTO **200 ms**, `tcp_rto_min_us`=200000; RFC 6298 recommends 1 s min — Linux deliberately deviates) or fast retransmit (3 dupACKs). RTO doubles each retry (exponential backoff). Idle connections: `tcp_slow_start_after_idle=1` (default) resets cwnd after one RTO of idle — bites keep-alive pools with bursty traffic.

## 2. Edge cases & gotchas

| # | Case | Why |
|---|------|-----|
| 1 | **Full accept queue, seen from the client**: some connects succeed instantly, later ones hang, `connect()` finally times out (Go: `dial tcp …: i/o timeout`) — not "connection refused". Verified: `listen(fd,1)` never accepting → 2 connects OK (backlog+1), 3rd..5th all hit my 4 s timeout. Client SYN retransmits at 1 s, 3 s, 7 s… | Kernel silently drops SYN (queue full) — no RST. Kernel `tcp_syn_retries=6` ⇒ ~67 s to last retry, 131 s total (kernel doc). |
| 2 | **Client thinks it is connected, server never saw it**: ACK dropped when accept queue full; client sends request, gets nothing, retransmits data; may sit until the server's SYN-ACK retry finds room. Symptom: request latency spikes of exactly 1 s / 3 s, `netstat -s`: "times the listen queue of a socket overflowed", "SYNs to LISTEN sockets dropped" | Client is ESTABLISHED after sending ACK; the server side is still SYN_RECV. |
| 3 | Backlog is a *per-listener* clamp; raising `somaxconn` does nothing unless the app's `listen(backlog)` is also large (Go uses somaxconn, so OK; nginx `listen … backlog=511` default; Java/Node often 50/511). | `min(backlog, somaxconn)`. |
| 4 | **Slow `Accept()` loop** is what fills the queue, not "too many clients": GC pause / blocked accept goroutine / fd exhaustion (`EMFILE`, Go http.Server retries with backoff up to 1 s). | Accept queue drains only at `accept()` speed. |
| 5 | **TIME_WAIT on the client side → port exhaustion.** Ephemeral range 32768–60999 (~28k ports); a client making >~470 short conns/s to ONE dst ip:port (28k/60 s) runs dry: `connect: cannot assign requested address` (EADDRNOTAVAIL). The tuple is (src ip, src port, dst ip, dst port) — different dst ⇒ no collision. | TIME_WAIT holds the 4-tuple 60 s. Real fix = reuse connections (pool), add source IPs/dst IPs, widen range; NOT tuning. |
| 6 | **`tcp_tw_reuse`**: values 0/1/2; **default 2 = loopback only** (kernel doc; container shows 2). 1 = global. Applies only to **outgoing** connect(), needs `tcp_timestamps` (uses timestamp monotonicity, PAWS), reuse allowed after ~1 s (`tcp_tw_reuse_delay`=1000 ms). Does nothing for a server accepting connections. | Safe because the new SYN carries a strictly larger timestamp than the old connection's last seen. |
| 7 | **`tcp_tw_recycle` was removed in Linux 4.12** (2017). It dropped SYNs from a host whose timestamp went backwards ⇒ multiple clients behind one NAT randomly failed to connect; killed entirely after per-connection timestamp offset randomisation. Any blog telling you to set it is pre-2017. `tcp_max_tw_buckets` (65536 here) just destroys TW sockets early with a log line — kernel doc says don't lower it. | PAWS + NAT + non-monotonic timestamps. |
| 8 | **SO_REUSEADDR vs SO_REUSEPORT.** REUSEADDR (Go sets it on every listener — verified `SO_REUSEADDR=1`): lets `bind()` succeed while old connections sit in TIME_WAIT (restart a server immediately). It does NOT let two live listeners share a port on Linux. REUSEPORT: multiple sockets (same uid) bind the same ip:port, kernel hashes 4-tuples across them (per-worker accept queues, no thundering herd); rolling restart trap: connections in a closed listener's accept queue are lost. Go: not exposed by `net.Listen`; set through `ListenConfig.Control` with `unix.SO_REUSEPORT`. Windows/BSD semantics differ. | Two options with confusingly similar names. |
| 9 | **RST on close with unread data**: `close()` on a socket whose receive buffer holds unread bytes sends **RST**, not FIN (RFC 1122/9293 behaviour). Verified in Go: client wrote "unread data", server `Close()`d without reading → client `Read` = `read: connection reset by peer` (ECONNRESET), and any response bytes in flight are discarded by the peer. Classic: HTTP server replies 4xx/413 and closes while client still uploads → client sees reset, never reads the error body. Remedy: `CloseWrite()` then drain the read side (net/http server does lingering read for this reason). | Kernel treats "data was received but never delivered" as an abort. |
| 10 | **EOF vs ECONNRESET vs EPIPE.** Clean FIN ⇒ `Read` returns `io.EOF`. RST ⇒ ECONNRESET. **Write after peer FIN**: 1st write succeeds (kernel buffers it, peer replies RST), 2nd write fails EPIPE — verified: `1st write after FIN: <nil>`, then `write: broken pipe`. Never trust "write returned nil" as delivery. Read side after RST ⇒ ECONNRESET, write side ⇒ EPIPE (or ECONNRESET if RST landed first). | FIN only closes one direction; the writer learns via the RST that the first write triggers. |
| 11 | **SIGPIPE in Go**: write to broken pipe on fd 1/2 kills the process; on any other fd (incl. sockets) it's just EPIPE (os/signal docs). `signal.Notify(SIGPIPE)` changes that for all fds. | Go runtime installs a handler and only re-raises for stdout/stderr. |
| 12 | **Half-close**: `TCPConn.CloseWrite()` sends FIN but keeps reading (verified: server got "req"+EOF, replied, client got "reply"). Used for request/response-by-EOF protocols and proxies (io.Copy both ways + CloseWrite on each direction). `Close()` = both directions; if unread data → RST (case 9). Go has `CloseRead` too (rarely useful, no wire effect). | FIN is per-direction. |
| 13 | **Nagle × delayed ACK stall.** Nagle: with unacked data in flight, hold *small* segments until ACK or full MSS. Receiver delays ACKs (Linux min 40 ms, max 200 ms; RFC 9293 says <500 ms). Write(header) + Write(body) + Read → second write waits for ACK of first, ACK waits for delay timer ⇒ ~40 ms per request. Verified on loopback: worst RTT 48 ms with NODELAY off vs 113 µs with it on (5 iterations of 10 B + 100 B writes). Fixes: NODELAY, or a single `Write` (build the buffer / `bufio` + Flush), `TCP_CORK`/`MSG_MORE`. NODELAY isn't free: tiny packets, more syscalls; hence "coalesce in userspace". Linux also has `tcp_autocorking` (coalesces when qdisc/NIC queue non-empty). | Two independent latency-saving heuristics deadlock each other for one timer. |
| 14 | **Go sets TCP_NODELAY by default** on both dialed and accepted TCPConns (source `newTCPConn` → `setNoDelay(fd,true)`; verified `NODELAY=1` on both ends). So Go clients rarely see #13 unless they call `SetNoDelay(false)`; but a *non-Go peer* (Python/C, or an L4 device) may. | Go designers chose latency over packet count. |
| 15 | **Slow start hurts small/new connections**: IW10 ≈ 14 KB in first flight; a 100 KB response on a fresh connection costs ~3 extra RTTs (10→20→40 segs). Reason #1 to reuse connections; cwnd also reset after idle (`slow_start_after_idle`). BDP: 1 Gbit/s × 100 ms = 12.5 MB in flight needed; default `tcp_rmem` autotuning caps it. | cwnd starts small to avoid congestion collapse. |
| 16 | **Zero window**: receiver app stops reading → rwnd=0 → sender stops and sends *window probes* (persist timer, exponential backoff, no limit — a stalled reader can pin the connection forever; probes don't count toward `tcp_retries2`-style death as long as they are ACKed). In Go: a peer that doesn't read makes your `Write` block → need write deadlines, or a slow client pins a goroutine + buffers. Silly-window / window update lost handled by probes. | Flow control is backpressure by design; the sender must be defended by timeouts, not TCP. |
| 17 | **Retransmission timeouts & how long a dead peer takes to notice**: unacked data is retried with doubling RTO until `tcp_retries2=15` ⇒ **~924.6 s (≈15.4 min)** hypothetical (kernel doc; real: first RTO > that). SYN: 6 retries ≈ 131 s. Blackholed peer (cable pulled, NAT entry gone, VM frozen): sender only finds out after ~15 min *if it has data to send*. | Backoff 200 ms→…→120 s cap (TCP_RTO_MAX). |
| 18 | **Idle dead peers are invisible**: a connection with no traffic and no keepalive stays ESTABLISHED forever after the peer vanished (no packets ⇒ no signal). Kernel keepalive: **OFF by default (SO_KEEPALIVE per-socket)**; when on: idle **7200 s**, interval **75 s**, **9** probes ⇒ ≈2 h + 11.25 min (kernel doc: "aborted after ~11 minutes of retries"). RFC 9293: SHOULD be off by default, idle ≥ 2 h (search summary; not opened). Half-open connections (peer rebooted): first write gets RST — only if peer's stack answers. | Detection needs traffic; keepalive *is* the traffic. |
| 19 | **Go keepalive defaults (verified, Go 1.24.7 source + master):** `net.Dialer.KeepAlive == 0` ⇒ enabled with idle **15 s**, interval **15 s**, count **9** (const `defaultTCPKeepAlive*`; observed via getsockopt: IDLE 15 INTVL 15 CNT 9, SO_KEEPALIVE 1). `KeepAlive: 30s` ⇒ IDLE 30, INTVL stays 15 (verified). `KeepAlive < 0` ⇒ SO_KEEPALIVE 0. `KeepAliveConfig{Enable,Idle,Interval,Count}` (Go 1.23+) takes precedence: verified Idle 10/Intvl 3/Cnt 4 applied. `http.DefaultTransport` dialer uses **KeepAlive: 30 s**. Servers: `net.Listen`/`ListenConfig` accepted conns also 15 s (verified `KEEPALIVE 1 IDLE 15` on accepted conn); `http.Server` therefore has kernel keepalive on. *Go's default is 15 s/15 s/9 ⇒ dead peer found in ≤ 15+9×15 = 150 s, NOT the 7200 s of the Linux sysctls.* Don't say "Go uses 7200". | Go 1.13 changed default from off/3 min listener; Go issue 31510 chose 15 s. |
| 20 | **Keepalive ≠ liveness of the application, and it ≠ NAT/LB idle-timeout fix unless idle < NAT timeout** (AWS NLB 350 s → 15 s fine; default 2 h is useless). It probes the *peer kernel*, so a hung app with a healthy kernel passes. Use app-level heartbeats (HTTP/2 PING, gRPC keepalive, WebSocket ping). | Kernel ACKs probes regardless of the process. |
| 21 | **TCP_USER_TIMEOUT** (ms, Linux ≥2.6.37): max time transmitted data may stay unACKed before the connection is killed with ETIMEDOUT; **overrides keepalive's probe-count logic** when both set (man tcp(7), via search summary — man7 unreachable). Doesn't change *when* retransmits happen. Use to cap the 15-min `tcp_retries2` window (e.g., 30 s for a DB client). Go: not in stdlib; `Dialer.Control` + `unix.TCP_USER_TIMEOUT`. Rule of thumb: keepalive idle+intvl×cnt ≥ user_timeout to avoid odd interaction (UNVERIFIED as guidance). | Bounds the "sent data, never ACKed" case, keepalive bounds the "idle" case. |
| 22 | **Head-of-line blocking**: TCP is an ordered byte stream — one lost segment holds back all later bytes to the app even though they arrived (SACK only helps retransmit efficiency). Multiplexed protocols on ONE connection (HTTP/2, gRPC) inherit it; a 1% loss link can make h2 slower than 6 h1 connections. Also *sender-side* HOL: a huge write blocks a small urgent message queued behind it (fix `TCP_NOTSENT_LOWAT`, per kernel doc set). | Ordering guarantee is per-connection, not per-stream. |
| 23 | **Go SetDeadline semantics** (verified): deadlines are **absolute times**, not idle timers — `SetReadDeadline(now+5s)` set once expires 5 s later even if data flowed; you must re-arm per operation. Applies to all current *and future* Read/Write; `time.Time{}` clears. Timeout error: `net.Error.Timeout()==true`, `errors.Is(err, os.ErrDeadlineExceeded)` (verified true both). After a timeout the conn is still usable (unlike Close) — but a partially-read message is now torn. `SetDeadline` sets both read and write. | Runtime netpoller timers, not TCP options. |
| 24 | **`conn.Close()` vs pending `Read` (verified):** Close from another goroutine unblocks the Read immediately with `use of closed network connection` (`errors.Is(err, net.ErrClosed)` true). Safe cancel pattern = Close (or `SetReadDeadline(time.Now())` to wake without closing). Context cancellation is NOT wired to a plain Conn.Read — only to Dial/Resolver/http. `Close` on a conn with a blocked *Write* (peer zero window) also unblocks it. Closing an already-closed conn returns ErrClosed. | netFD refcount + poller wake-up. |
| 25 | **`net.Dialer.Timeout`/ctx deadline is split across addresses** (`partialDeadline`): hostname with N A records, ctx 30 s ⇒ first dead address gets ≈30/N s. Not a TCP thing but explains "connect timeout much shorter than configured". Go also races IPv4/IPv6 (see net-dns-lb). | dialSerial divides remaining budget. |

## 3. Common misconceptions
- "TIME_WAIT is on the server / is a leak / lower `tcp_fin_timeout`" → it's on whoever closed first; fixed 60 s on Linux; `tcp_fin_timeout` concerns FIN_WAIT_2. Many TIME_WAITs on a *server* means the server closes first (e.g., HTTP/1.0 or `Connection: close`), harmless unless it's a client port-exhaustion case.
- "Set `tcp_tw_recycle=1` / `tcp_tw_reuse=1` to fix TIME_WAIT" → recycle is gone since 4.12 and broke NAT; reuse only helps outbound connects, needs timestamps.
- "SO_REUSEADDR lets two servers share a port" → not on Linux (that's REUSEPORT).
- "Full backlog → ECONNREFUSED" → Linux default drops silently; refused (RST) only with closed port or `tcp_abort_on_overflow=1`.
- "Write returned nil so it arrived" → it only means data is in the kernel send buffer.
- "TCP keepalive defaults to 2 h so dead peers are noticed in 2 h" → only if enabled; off by default; Go enables it at 15 s.
- "TCP_NODELAY must be enabled in Go" → already default. "Nagle is bad" → only for write-write-read patterns; bulk streams like it.
- "Close() sends FIN" → only if the receive buffer is empty; unread data ⇒ RST.
- "Go's `SetReadDeadline` is an idle timeout" → absolute; re-arm each call.
- "SYN cookies make the server faster / fix backlog" → last-resort flood defence; disables some TCP options.

## 4. Go tie-ins (all verified unless noted)
- `net.Listen` → `SO_REUSEADDR=1`, backlog from `/proc/sys/net/core/somaxconn`; accepted conns: NODELAY on, keepalive 15 s.
- `net.Dialer{KeepAlive, KeepAliveConfig, Timeout, FallbackDelay(300 ms default), Control}`; `TCPConn.SetNoDelay/SetKeepAlive/SetKeepAlivePeriod/SetKeepAliveConfig/CloseWrite/CloseRead/SyscallConn`.
- `http.DefaultTransport`: dial timeout 30 s, KeepAlive 30 s, `IdleConnTimeout` 90 s, `MaxIdleConnsPerHost` 2 (DefaultMaxIdleConnsPerHost) — the 2 is why bursty fan-out clients churn connections and pile up TIME_WAIT/EADDRNOTAVAIL; raise it.
- `http.Server` with no `IdleTimeout` and no `ReadTimeout` keeps idle keep-alive connections forever (docs: IdleTimeout falls back to ReadTimeout) — kernel keepalive at 15 s still frees dead peers, but live idle ones stay.
- Reading is goroutine-per-conn: a dead-but-not-RST peer parks the goroutine in netpoll until keepalive (≤150 s) or a deadline fires; without deadlines, leak.
- Go runtime ignores SIGPIPE on sockets → EPIPE; `errors.Is(err, syscall.EPIPE)` / `ECONNRESET` for classification; `io.EOF` for clean close, `io.ErrUnexpectedEOF` for truncated framed read.
- Go 1.26: no change found to these defaults (release notes + master source). Local runtime was 1.24.7; `UNVERIFIED` only in the sense that I could not execute on 1.26 binary.

## 5. Illustration plan
**Scene A — "The two queues" (7 frames)**
1. Client, SYN queue (small box), accept queue (box), server app with `accept()`. Point: two queues, two limits.
2. SYN → enters SYN queue, SYN-ACK back. Point: server state = SYN_RECV, client still waiting.
3. ACK → connection hops to accept queue; `accept()` pops it. Point: `accept()` speed, not connection speed, drains it.
4. **STOP:** accept loop stalls, accept queue full (`min(backlog, somaxconn)`) — 3rd client's ACK/SYN silently dropped. Client shows "connected" (ACK sent) or SYN retrying 1 s, 3 s, 7 s. Question: "what does the client see?" → timeout, not refused.
5. `tcp_abort_on_overflow=1` variant: RST instead → client "reset". Point: drop is deliberate (lets bursts recover).
6. SYN flood: SYN queue overflows → SYN cookie in ISN, no state kept, ACK reconstructs. Point: fallback only, options lost.
7. Counters: `ListenOverflows`, `ListenDrops`; fix = faster accept, bigger backlog. 

**Scene B — "TIME_WAIT and its ring" (8 frames)**
1. Active closer sends FIN, gets ACK (FIN_WAIT_2). 2. Peer FIN → active side ACKs → TIME_WAIT (clock ring 60 s = 2×MSL). 3. **STOP:** why wait? Frame shows final ACK lost → peer retransmits FIN; a gone socket would answer RST. 4. Second reason: old duplicate segment wandering in network hits new connection with same 4-tuple (ring of 4-tuple). 5. Client port pool of 28k ports drains: `cannot assign requested address`. 6. Fixes: connection pooling, more dst IPs / src IPs, `tcp_tw_reuse=1` (outbound only, timestamps, 1 s). 7. **STOP:** `tcp_tw_recycle` — NAT box with two hosts, timestamps disagree, SYN dropped; stamp "removed in 4.12". 8. REUSEADDR: restart server, bind works despite TIME_WAIT; REUSEPORT: two listeners share port.

**Scene C — "Close is not one thing" (8 frames)**
1. Ladder: clean close, FIN → reader gets EOF. 2. Half-close: `CloseWrite`, peer keeps replying. 3. Server closes with unread bytes in buffer → **RST** (red). 4. Client blocked `Read` → ECONNRESET, response body lost. **STOP:** "why did my 413 never reach the client?" 5. Write after FIN: 1st write OK, RST returns, 2nd write EPIPE. 6. Go: SIGPIPE only kills on fd 1/2. 7. Dead peer, no traffic: silent; keepalive probe ladder 15 s/15 s×9 (Go) vs 7200/75×9 (kernel). 8. **STOP:** blackholed peer with data in flight → RTO doubling to ~15 min; `TCP_USER_TIMEOUT` cuts it.

**Scene D — "Small packets, big stalls" (7 frames)**
1. write(header) leaves; write(body) held by Nagle (timeline strip). 2. Receiver waits to piggyback ACK (40 ms timer). 3. **STOP:** 40 ms bar appears; interviewer: "why exactly 40 ms?" 4. NODELAY: both segments go immediately; Go default. 5. Or one buffered write. 6. Slow start: cwnd boxes 10→20→40 vs response size; new conn vs warm conn. 7. Zero window: reader stalls, window closes, probes; Go `Write` blocks → write deadline.
