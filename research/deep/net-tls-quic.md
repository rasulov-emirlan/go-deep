## 1. Mechanism

**TLS 1.3 full handshake (1-RTT):** ClientHello (supported groups + key_share(s), SNI, ALPN, supported_versions, optional PSK) → ServerHello (chosen key_share) — everything after is encrypted: EncryptedExtensions (ALPN result), Certificate, CertificateVerify, Finished → client Finished. App data can flow from the client right after its Finished (1 RTT); the server can send data after its Finished (before the client's — that early server data is only to an unauthenticated-yet client). Over TCP total to first request byte = 1 RTT (TCP) + 1 RTT (TLS) = 2 RTT; QUIC merges transport+TLS = 1 RTT.
**Resumption:** after the handshake the server sends NewSessionTicket (a PSK identity, usually a self-encrypted ticket — *stateless* server). Next connection: ClientHello carries `pre_shared_key` (+ psk_key_exchange_modes; use `psk_dhe_ke` to keep forward secrecy) → abbreviated handshake, no certificate exchange, still 1 RTT. **0-RTT (early data):** client also sends application data encrypted under a key derived from the PSK in the first flight ⇒ request in 0 extra RTT. Costs: **no forward secrecy for early data, no replay protection** — RFC 8446 §8 (search summary): "no guarantees of non-replay between connections"; servers MUST ensure at most-once acceptance *per server instance* (so N instances ⇒ up to N replays); ticket-key compromise decrypts early data. HTTP mitigation: RFC 8470 — the terminating proxy adds `Early-Data: 1` to the request; the origin answers **425 Too Early** if it can't safely process; the client then retries after handshake completes. Safe in 0-RTT: idempotent, side-effect-free (GET on static/cacheable content, not "GET /transfer?…"); unsafe: POST, anything with state change, one-time tokens, counters, rate-limit accounting.

**Chain of trust & revocation:** server must send leaf + all intermediates (root excluded); client builds path to a local trust anchor. Revocation reality: CRL (big, stale), OCSP (per-cert online query: privacy leak, latency, soft-fail so attackers just block it), **OCSP stapling** (server attaches a fresh signed OCSP response; helps, but only "must-staple" makes it hard-fail), CRLite/CRLSets (browser-pushed compressed revocation lists). Short-lived certs (Let's Encrypt 90 d → shorter) are the real mitigation.

**QUIC (RFC 9000/9001/9002):** transport + TLS 1.3 (TLS handshake messages carried in CRYPTO frames; packet protection keys from TLS) over UDP. Streams are independent: loss on one stream blocks only that stream's delivery (per-stream ordering), unlike TCP where one lost segment blocks the whole byte stream. Connection identified by **Connection IDs**, not the 4-tuple ⇒ **migration**: client changes IP/port (Wi-Fi→LTE, NAT rebinding), keeps sending with a fresh CID; peer sends **PATH_CHALLENGE**(8 random bytes)/PATH_RESPONSE to validate the new path before sending lots of data (anti-amplification/off-path attacker). Client Initial datagrams must be padded to **≥1200 bytes** (RFC 9000 §14) — also implies path must carry 1200-byte UDP without fragmentation; QUIC does its own PMTU discovery (DPLPMTUD, RFC 8899) upward from there.

## 2. Edge cases & gotchas

| # | Case | Why |
|---|------|-----|
| 1 | **0-RTT replay ⇒ which requests are safe.** Only requests that are safe to run twice: idempotent *and* free of observable side effects (GET/HEAD of cacheable data). Not POST/PUT-with-effects, not login, not OTP/nonce redemption. The server can't distinguish a replay from the original; even "idempotent" DELETE replays after a re-create is harmful. Defence in depth: single-use ticket store/strike register (per-instance only; shared store costs a round trip), reject early data at the origin with 425, or disable 0-RTT. quic-go's `http3.Server` **enables 0-RTT by default at the QUIC layer** (search summary of quic-go docs), and exposes `http3.MethodGet0RTT` for GET-only early data — check your version. | Early data is encrypted only under the resumption PSK; no server randomness bound into the key. |
| 2 | **Go's `crypto/tls` does not implement 0-RTT** (server or client): Go comment in `handshake_server_tls13.go` "because 0-RTT is not supported"; a client sending `early_data` w/o PSK is rejected. So a Go origin behind CDN sees `Early-Data: 1` only from a CDN that does 0-RTT; the Go server itself never accepts early data on TLS/TCP. For QUIC 0-RTT you use quic-go. | Deliberate omission; replay-protection story is hard in a library. |
| 3 | **Session tickets**: (a) *Server side, Go:* `tls.Config` auto-generates ticket keys, **rotates daily and drops after 7 days** (verified in `common.go`: `ticketKeyRotation=24h`, `ticketKeyLifetime=7d`, `maxSessionTicketLifetime=7d`). In a multi-instance fleet each instance has its own random key ⇒ resumption only works if the client hits the same instance; share keys with `Config.SetSessionTicketKeys` (first key encrypts, others decrypt), rotate on your own schedule. (b) *Compromise of ticket key breaks forward secrecy of all resumed sessions for its lifetime* — hence short rotation. (c) *Go client:* resumption works **only if `Config.ClientSessionCache` is set** (verified: `DidResume` false on both dials without cache; with `tls.NewLRUClientSessionCache` first false, second **true**). `http.Transport`'s default TLS config has no cache ⇒ **Go HTTP clients do full handshakes on every new connection** unless you configure `TLSClientConfig.ClientSessionCache`. (d) Resumed handshakes **skip `GetCertificate`** (verified: 4 dials, 1 resumed ⇒ `GetCertificate` called 3 times, none for the resumed one) — a rotated server cert isn't presented on resumed connections; a revoked/rotated cert stays "valid" until ticket expiry. | PSK identity is the ticket; cert exchange not repeated. |
| 4 | **SNI & ECH.** SNI is plaintext in ClientHello ⇒ on-path observers (and DPI, SNI-routing L4 proxies) see the hostname. **ECH (Encrypted Client Hello)** encrypts the inner ClientHello (incl. SNI, ALPN) under a public key fetched via DNS HTTPS/SVCB record (`ech=` param); outer ClientHello carries a "public name" (e.g., the CDN's shared name). Now **RFC 9849** (search summary: made official 2026-03-03, Standards Track); deployed by Cloudflare, Firefox ≥119, Chrome. Go: **client ECH since 1.23** (`Config.EncryptedClientHelloConfigList`; draft-18 at the time), **server ECH since 1.24** (`EncryptedClientHelloKeys`), `GetEncryptedClientHelloKeys` in 1.25 (verified in release notes). Gotchas: needs DoH/DoT-protected DNS to be meaningful (else DNS leaks the name); SNI-based routing/WAF at the edge must run *behind* ECH termination; on decryption failure (stale key) server sends `retry_configs`. No SNI ⇒ Go `GetCertificate` gets empty `ServerName`. | Metadata privacy vs middlebox visibility. |
| 5 | **Missing intermediates** — "works in Chrome, fails in curl/Go/Java". Server sent only leaf. Browsers may fetch the issuer through the AIA `caIssuers` URL or reuse cached intermediates; Go/OpenSSL/curl don't (Go `x509` has no AIA fetching — no such code in `verify.go`). Verified: leaf-only server ⇒ client error `tls: failed to verify certificate: x509: certificate signed by unknown authority`; adding the intermediate to `tls.Certificate.Certificate[1:]` ⇒ OK. Debug: `openssl s_client -showcerts`, SSL Labs "chain issues: incomplete". Also: cross-signed chains / expired legacy root in the served chain ⇒ old Android/OpenSSL 1.0.x fail; serve the shortest chain, order leaf→intermediates, don't include the root. In Go, `tls.LoadX509KeyPair` reads all PEM blocks from the cert file — put the full chain (fullchain.pem), not just cert.pem. | Path building is the client's job, but only if it has the intermediates. |
| 6 | **OCSP stapling & revocation reality.** Go: server can staple via `tls.Certificate.OCSPStaple` (**static bytes — you must refresh it yourself** and return a new `*Certificate` from `GetCertificate`; Go does not fetch OCSP); client sees `ConnectionState.OCSPResponse` but **Go's verifier does no revocation checking at all** (no CRL/OCSP) — you must do it in `VerifyPeerCertificate`/`VerifyConnection` if needed. Let's Encrypt shut its **OCSP responders down Aug 6 2025** (Must-Staple issuance failed from May 7 2025; OCSP URLs removed from certs; CRLs instead) (search summary of LE announcements). Browsers: Chrome doesn't do live OCSP (CRLSets), Firefox CRLite. Interview line: "revocation is best-effort; soft-fail defeats it; short-lived certs are the mitigation." | Live checks leak privacy and add latency; blocked = attacker wins if soft-fail. |
| 7 | **mTLS in service meshes & rotation.** Istio: sidecar (Envoy + pilot-agent) requests SPIFFE workload certs from istiod, **24 h default lifetime, rotated at ~50 % of lifetime** (`SECRET_TTL` 24h, grace ratio 0.5; search summary of Istio docs) via SDS — Envoy swaps certs in memory, existing connections keep the old cert until they end, new handshakes use the new. Problems: clock skew (`NotBefore` in the future ⇒ `certificate is not yet valid`), trust-bundle rollover (old root must stay in the pool while new certs issued — root transition), long-lived connections never re-handshake so they never see expiry until close (Go: TLS 1.3 has no renegotiation; expiry is checked only at handshake), CA outage ⇒ certs expire after 24 h. The mesh terminates TLS in the sidecar — your Go app speaks plaintext to localhost; app-level identity via `X-Forwarded-Client-Cert`, not `r.TLS`. | Cert lifetime shorter than connection lifetime; check happens only at handshake. |
| 8 | **Go cert rotation without restart.** *Server:* `tls.Config.GetCertificate` is called per handshake (only when SNI present or `Certificates` empty — doc) → return a cached `*tls.Certificate` swapped atomically (`atomic.Pointer[tls.Certificate]`) after re-reading files on fsnotify / ticker; **don't reload from disk in every call** (CPU/IO on every handshake). `GetConfigForClient` if you need per-client config (e.g., changing `ClientCAs`, ticket keys). *Client:* `GetClientCertificate` is called when the server requests a cert (can be invoked multiple times with TLS 1.3) — same atomic swap. **k8s Secret mounts** update via atomic symlink swap (`..data`); watching the file itself with inotify misses it — watch the directory/`..data`. `tls.Config` must not be modified after use (docs: clone or use callbacks); swapping `srv.TLSConfig` on a running `http.Server` doesn't affect the listener. Existing connections keep the old cert (fine). Resumed sessions skip `GetCertificate` (case 3d). `autocert`/certmagic do this for ACME. | Config is snapshot at Serve; callbacks are the supported hooks. |
| 9 | **ALPN.** Client lists `NextProtos` (`h2`, `http/1.1`); server picks; result in `ConnectionState.NegotiatedProtocol` (verified: server `[h2,http/1.1]`, client `[h2]` ⇒ `h2`). If no overlap and both sent ALPN, Go server **aborts** with alert `no_application_protocol` (verified: `remote error: tls: no application protocol`) — this is how HTTP/2 vs 1.1 and mTLS-mesh protocol gating (`istio` ALPN, gRPC needs `h2`) work. `http.Server.ServeTLS`/`ListenAndServeTLS` **adds `h2`/`http/1.1` to NextProtos automatically** (`adjustNextProtos`); if you hand `http.Serve` a `tls.NewListener(...)` with a custom config you must include `"h2"` yourself or you silently get HTTP/1.1. ALPN also picks QUIC's `h3`. Custom `TLSNextProto` non-nil empty map disables h2. | ALPN happens inside the handshake ⇒ no extra RTT. |
| 10 | **TLS termination trade-offs.** *At LB/ingress (L7):* central cert mgmt, WAF/routing on paths, HTTP/2↔1.1 translation, connection reuse to backends; but plaintext inside your network unless re-encrypted (mesh/mTLS), LB sees secrets, client IP requires XFF/PROXY. *Passthrough (L4, SNI routing):* end-to-end encryption, LB can't inspect/retry HTTP, only SNI (or nothing with ECH!). *Terminate + re-encrypt* costs an extra handshake CPU but keeps compliance. Also **TLS handshake CPU** at the edge (ECDSA P-256 ≪ RSA-2048 for server signing; Go picks based on cert), session resumption offloading, and **large ClientHellos**: Go ≥1.24 sends hybrid **X25519MLKEM768** by default (release notes; `tlsmlkem=0` reverts) ⇒ ClientHello > ~1.1 KB, spills over multiple segments; some middleboxes/servers hang on it ("TLS post-quantum TL;DR fail" cited in the notes) — a *new* "handshake hangs for Go 1.24 clients only" bug class. Go 1.26 adds SecP256r1MLKEM768 / SecP384r1MLKEM1024 defaults (`tlssecpmlkem=0`). | Bigger key shares ⇒ multi-packet hello ⇒ ossified middleboxes. |
| 11 | **HOL blocking, three levels.** HTTP/1.1: per-connection request serialisation (browsers open ~6 conns). HTTP/2: streams multiplexed on one TCP connection — fixes app-level HOL but **TCP-level HOL remains**: one lost segment stalls all streams; on lossy links (1–2 % loss) h2 can be slower than several h1 connections. HTTP/3/QUIC: loss affects only streams whose packets were lost (per-stream ordering); but connection-level **flow control and congestion control** are still shared, so one stream can still starve others; and QUIC is implemented in user-space (CPU cost, no kernel offload/GSO limits ⇒ 1.5–3× CPU at high throughput — UNVERIFIED number). | Ordering scope: byte stream (TCP) vs per-stream (QUIC). |
| 12 | **QUIC migration & connection IDs.** Servers issue several CIDs (NEW_CONNECTION_ID); client rotates on path change so passive observers can't link paths. Migration needs the LB to route by CID, not 4-tuple (**QUIC-LB**: encode server-ID in CID; otherwise ECMP/L4 LBs break migration and even normal multi-packet flows → "connection reset after NAT rebind"). NAT rebinding without migration: UDP NAT timeouts are short (often 30 s–2 min) ⇒ QUIC idle keep-alive PINGs matter; RFC 9308/9312 note middleboxes use arbitrary UDP timeouts. Server only migrates *client* address (server address migration = preferred_address transport param). Path validation blocks amplification: before validation, at most 3× received bytes. | UDP flows lack a connection identity, so QUIC brings its own. |
| 13 | **UDP blocked/throttled ⇒ fallback.** RFC 9308 (search summary): 3–5 % of networks block UDP (and enterprises block 443/UDP). Browsers race/fallback: h3 learned from `Alt-Svc: h3=":443"; ma=86400` (or HTTPS RR) on a prior TCP response, then try QUIC; on failure mark the origin "broken" and use TCP+h2, adding latency (roughly a QUIC handshake timeout, ~ hundreds of ms–seconds). So **h3 is an upgrade never the only path**: always keep TCP/TLS listener on same port, `Alt-Svc` header, and monitor h3 share. Server-side gotchas: firewall/security group must allow **UDP/443** (people open only TCP), `net.core.rmem_max` too small ⇒ quic-go warns "failed to sufficiently increase receive buffer size" (~7 MB wanted), UDP GRO/GSO. | UDP is treated as second-class by middleboxes. |
| 14 | **MTU/PMTUD black hole: "works for small requests, hangs for large ones".** Handshake (small packets) and small GETs work; a big POST body, a TLS Certificate flight, or a large response stalls forever/retransmits. Cause: some link on the path has MTU < 1500 (VPN/IPsec/WireGuard 1420, VXLAN overlay 1450, PPPoE 1492, GRE, cloud tunnels) and ICMP "Fragmentation needed"(v4)/"Packet Too Big"(v6) is filtered, so the sender keeps sending DF packets that vanish. Symptom fingerprint: SYN/SYN-ACK fine, first full-size segment retransmits, `tcpdump` shows retransmissions of 1500-byte frames and no ACK; `ping -M do -s 1472 host` fails, `-s 1372` works. Fixes: **MSS clamping** at the tunnel/edge (`iptables … -j TCPMSS --clamp-mss-to-pmtu`, or `--set-mss`), fix MTU on the interface/CNI (k8s CNI MTU), **allow ICMP type 3 code 4 / ICMPv6 type 2**, Linux `net.ipv4.tcp_mtu_probing=1` (kernel doc: enabled only when ICMP black hole detected) or 2 (always, starts at `tcp_base_mss`) → PLPMTUD (RFC 4821). **QUIC** has no MSS; it starts at 1200 and probes up (DPLPMTUD), so it degrades more gracefully but a path with MTU <1280 (IPv6 minimum) or filtering of >1200 datagrams breaks it. ML-KEM hybrid ClientHello (case 10) manifests the same way: only handshakes with big hellos hang. | PMTUD relies on ICMP that middleboxes drop; clamping bypasses the need. |
| 15 | **Go's HTTP/3 status.** **stdlib has no HTTP/3 (through Go 1.26)**: 1.26 release notes list none. Work in progress: `golang.org/x/net/quic` (experimental QUIC, accepted proposal #58547, exists; package still API-unstable), `x/net/internal/http3` (proposal #70914; "implemented in internal package" as of mid-2026 per search summary), and a proposal #77440 (Feb 2026) for pluggable HTTP/3 in `net/http` — none shipped as public API (UNVERIFIED on exact state; search summary). `crypto/tls` has `QUICConn` (+ 1.26 handshake-error event) as the hook for third-party QUIC stacks. Production choice: **`github.com/quic-go/quic-go` + `/http3`** (RFC 9000/9001/9002, DPLPMTUD RFC 8899, QUIC v2 RFC 9369, datagrams RFC 9221, HTTP/3 RFC 9114, QPACK 9204, WebTransport/MASQUE in sibling repos; from README fetched 2026-09; v0.60+ FIPS mode with Go 1.26). Used by Caddy, cloudflared, Syncthing. Typical wiring: TCP `http.Server` sets `Alt-Svc` via `http3.Server.SetQUICHeaders`, and a UDP listener serves h3 on the same port. | net/http's internals assume a TCP `net.Conn`. |
| 16 | **TLS versions/ciphers Go defaults**: TLS 1.2 minimum for servers since Go 1.22 (1.26 notes: default min 1.2 for clients and servers once `tls10server` GODEBUG sunsets); TLS 1.3 cipher suites are not configurable (`CipherSuites` only affects 1.2); 1.25 disallows SHA-1 sigalgs in TLS 1.2 (`tlssha1=1` restores); TLS 1.3 preferred by servers even if client prefers 1.2 (1.25). `InsecureSkipVerify` with a custom `VerifyPeerCertificate` is the only way to add pinning yet keep custom verification; `VerifyConnection` runs also on resumption. | Secure defaults evolve by release; GODEBUG knobs mark deprecations. |

## 3. Common misconceptions
- "TLS 1.3 is 0-RTT" → default is 1-RTT; 0-RTT only on resumption, replayable, and no FS for early data.
- "0-RTT is safe for GETs" → safe only if GETs truly have no side effects; replay may also leak timing/cache state.
- "HTTP/3 removes head-of-line blocking completely" → only transport-level per-stream; congestion/flow control are connection-wide.
- "HTTP/3 = TLS-less" or "QUIC is UDP so unreliable" → QUIC is reliable, congestion-controlled, always encrypted (TLS 1.3 mandatory).
- "ECH is just encrypted SNI" → it encrypts the whole inner ClientHello; needs HTTPS RR keys in DNS.
- "OCSP stapling means revocation is solved" → without must-staple the client soft-fails; Go doesn't check revocation at all; Let's Encrypt has no OCSP since Aug 2025.
- "Browsers loaded it, so my chain is fine" → AIA fetching/caching hides missing intermediates.
- "Session resumption is automatic in Go" → server yes; client only with a `ClientSessionCache`.
- "Restarting is needed to rotate certs" → not with `GetCertificate`/`GetClientCertificate`; but existing connections keep old certs.
- "Small requests work, large hang → the server is slow" → check MTU/ICMP/MSS.
- "Go supports HTTP/3 in `net/http`" → not as of 1.26; use quic-go.

## 5. Illustration plan
**Scene A — "One RTT, or none?" (8 frames):** 1. Ladder TCP SYN/SYN-ACK then ClientHello/ServerHello…Finished (2 RTT to first byte). 2. NewSessionTicket arrives, client stores it (ticket card). 3. Resumption: ClientHello+PSK — no cert flight. 4. 0-RTT: request rides in first flight (green speed line). **STOP:** "what can go wrong?" 5. Attacker copies the first flight, replays to another server instance (red duplicate) — "POST /pay" executes twice. 6. Defences: strike register (per instance), 425 Too Early + `Early-Data:1`, only safe methods. 7. Go: server has no 0-RTT; client without `ClientSessionCache` resumes never. 8. Ticket key rotation ring: new daily, kept 7 days; two instances with different keys ⇒ resumption miss.

**Scene B — "The chain and the certificate that isn't there" (7 frames):** 1. Trust tree root→intermediate→leaf; server sends [leaf]. 2. Chrome quietly fetches the intermediate via AIA → green lock. 3. curl/Go fails: `unknown authority` (red). **STOP.** 4. Fix: fullchain (leaf+intermediate). 5. Revocation strip: CRL, OCSP (soft-fail), stapling, must-staple; LE OCSP off Aug 2025. 6. Rotation: new cert file appears, `GetCertificate` swaps pointer; new handshakes get new cert. 7. Long-lived connection keeps old cert; resumed handshake skips cert entirely.

**Scene C — "Three kinds of head-of-line" (8 frames):** 1. HTTP/1.1: one lane per connection. 2. HTTP/2: many streams, one TCP lane. 3. Lost packet: **whole lane** freezes (red). **STOP.** 4. QUIC: same streams, independent lanes; only stream 3 waits. 5. Connection ID ring: phone hops Wi-Fi→LTE, same CID, PATH_CHALLENGE/RESPONSE. 6. Middlebox drops UDP/443 → client falls back to TCP+h2 (Alt-Svc + broken-origin flag). 7. Shared congestion window still connection-wide. 8. Go: stdlib none, quic-go serves h3 + Alt-Svc from the TCP server.

**Scene D — "Small works, big hangs" (7 frames):** 1. Path with tunnel MTU 1420 in the middle. 2. SYN/handshake small ⇒ OK. 3. Big response segment (1500 B, DF) hits the tunnel; router drops it and sends ICMP "frag needed". 4. Firewall eats the ICMP (red) ⇒ sender retransmits same size forever (black hole). **STOP:** interviewer: "why do small requests work?" 5. Fix A: MSS clamp at the edge rewrites SYN MSS to 1380. 6. Fix B: allow ICMP / `tcp_mtu_probing=1`. 7. Go 1.24 hybrid ML-KEM hello (>1 KB, multi-packet) hits an old middlebox — same "only some clients hang" shape; `tlsmlkem=0`. QUIC's 1200-byte floor & DPLPMTUD contrast.
