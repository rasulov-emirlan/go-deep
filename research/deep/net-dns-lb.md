## 1. Mechanism

**DNS as a load-distribution/failover tool, naive → real.** Naive: "point A record at N IPs, lower TTL, done". Reality is a stack of caches, each with its own opinion of TTL:
`app (JVM/Go http.Transport: connection pool pins the IP, no DNS at all after connect)` → `libc/stub (nscd, systemd-resolved)` → `node-local cache (k8s NodeLocal DNSCache)` → `cluster DNS (CoreDNS)` → `recursive (ISP/8.8.8.8, floors/ceilings TTL)` → `authoritative`.
- Records are cached for TTL at every layer; some recursives clamp (min TTL floors, serve-stale on failure). Failover time ≈ TTL_recursive + how long clients keep old connections/IPs — **connections outlive TTL**. Health-checked DNS failover therefore cannot move already-established long-lived connections; it only steers *new* dials.
- **Negative caching** (RFC 2308 — from memory, not opened): NXDOMAIN/NODATA cached for the zone's SOA `minimum` (capped by the SOA TTL). A name you create *right after* a client looked it up stays "not found" for that long. In k8s this shows up during deploys ("service doesn't resolve for 30 s after creation").
- **Round-robin DNS** = client-visible list of A/AAAA; order rotated by server, but clients sort (RFC 6724) and often take first. Gives crude spreading, no health awareness, no weights.

**Resolver in Go.** Two implementations: pure-Go (default on Linux when `/etc/nsswitch.conf`/`resolv.conf` are "simple") and cgo → `getaddrinfo`. Selection (`net/conf.go`): `Resolver.PreferGo` → `GODEBUG=netdns=go|cgo` (+`+1`/`+2` for debug) → build tags `netgo`/`netcgo` → otherwise Go prefers pure-Go but falls back to cgo on unusual nsswitch/resolv.conf options, unreadable resolv.conf, or unknown option. The Go resolver **has no TTL cache** (only in-flight `singleflight` dedup); it re-reads `/etc/resolv.conf` at most every 5 s. Defaults: `ndots:1`, `timeout:5s`, `attempts:2` (`dnsconfig_unix.go`); container here has `timeout:2 attempts:3` from resolv.conf. A and AAAA are sent **in parallel from separate UDP sockets** (verified with a fake DNS server: same lookup produced two queries from different source ports, 35050 and 39917).

**Load balancing layers.** L4 (NLB, IPVS, kube-proxy, HAProxy tcp mode): picks a backend per *connection* (5-tuple hash / RR), never parses bytes; cheap, preserves TLS end-to-end, can't retry an HTTP request. L7 (ALB, Envoy, nginx, HAProxy http): terminates the client connection, opens/reuses its own upstream connections, balances per *request*, can retry, add headers (XFF), route by path, do gRPC-aware balancing.
Why gRPC breaks L4 balancing: HTTP/2 multiplexes all RPCs on **one long-lived TCP connection**; the L4 LB balanced exactly once at connect; new pods after scale-out get zero connections; hot pods stay hot. grpc-go default policy is `pick_first` (one connection to the first address) — even if DNS returns 10 IPs. Remedies: (1) L7 proxy that understands h2 (Envoy/Istio/linkerd) → per-RPC; (2) client-side LB: `round_robin` service config + `dns:///` target + headless Service (one subchannel per pod IP); (3) server `keepalive.ServerParameters.MaxConnectionAge` (default infinity; ±10 % jitter added; `MaxConnectionAgeGrace` extra time before force close) → GOAWAY, client reconnects and re-balances; (4) xDS/lookaside LB.

## 2. Edge cases & gotchas

| # | Case | Why |
|---|------|-----|
| 1 | **ndots:5 amplification (k8s).** Pod `resolv.conf`: `search <ns>.svc.cluster.local svc.cluster.local cluster.local` + `options ndots:5` (verified in k8s docs). Name with < 5 dots (`api.stripe.com` = 2) is tried against every search suffix first: `api.stripe.com.<ns>.svc.cluster.local`, `…svc.cluster.local`, `…cluster.local` (+ node suffixes on cloud, e.g. `ec2.internal`) each returning NXDOMAIN, and only then the absolute name — ×2 for A and AAAA ⇒ 8–10 queries for one lookup. Go implements exactly this (`nameList`: unsuffixed first only if dots ≥ ndots). Fixes: FQDN with trailing dot (`api.stripe.com.`), `dnsConfig.options: ndots: 1–2` per pod, NodeLocal DNSCache, autopath plugin in CoreDNS. K8s allows ≤32 search domains / 2048 chars total. | Search list heuristics designed for short intra-cluster names (`svc`, `svc.ns`), which need up to 5 dots for fully qualified `svc.ns.svc.cluster.local`. |
| 2 | **DNS TTL ≠ failover time.** Even with TTL 30 s, clients holding pooled connections keep talking to the old IP (Go `http.Transport` reuses idle conns up to `IdleConnTimeout` 90 s and active ones indefinitely); JVM caches DNS per `networkaddress.cache.ttl`; some libs resolve once at startup. Go: no resolver cache, but each *new dial* resolves, so the lag is the connection lifetime. Mitigation: bound connection lifetime (server MaxConnectionAge / `Connection: close` periodically / client `MaxIdleConns`+`IdleConnTimeout`), don't rely on DNS for fast failover — use VIP/anycast/L7 health checks. | Caches at every layer + connection pinning. |
| 3 | **Negative caching** keeps NXDOMAIN (and SERVFAIL for shorter periods) — race at deploy: client asks before record exists, cached "no such host" for SOA-minimum seconds. Go surfaces `no such host` (`*net.DNSError{IsNotFound:true}`); `IsTemporary`/`IsTimeout` differ — retry only the latter. Verified fake NXDOMAIN gives `lookup api.example.com on 8.8.8.8:53: no such host`. | RFC 2308 caches the *absence*. |
| 4 | **5-second DNS stall (k8s / conntrack race).** glibc (and musl) send A and AAAA **from the same socket (same 5-tuple) in parallel**; with kube-proxy DNAT (service IP → CoreDNS pod), both packets can race through netfilter before the conntrack entry is confirmed; two entries are created for one tuple, the second insertion fails ("clash") and the packet is dropped ⇒ one answer never returns ⇒ resolver waits `timeout` (glibc default **5 s**) then retries ⇒ exactly 5 s (or 10 s) tail latency. Weave post (Aug 2018) + kubernetes/kubernetes#56903. Mitigations: `options single-request-reopen` (separate sockets — glibc only, not musl/Alpine), NodeLocal DNSCache (skips DNAT/conntrack; upgrades upstream to TCP — verified in k8s docs), kernel fixes (conntrack clash resolution in 4.19/5.0-era kernels — **UNVERIFIED versions**), or TCP DNS (`use-vc`). **Go is mostly immune to the same-socket race** (verified: A and AAAA use different source ports), but Go's own 5 s `timeout` default means any dropped UDP costs 5 s also. `nf_conntrack_udp_timeout` = 30 s default (k8s docs); full conntrack table drops new flows. | UDP has no handshake; parallel same-tuple packets race on conntrack insert. |
| 3b | Careful phrasing for interviews: the root cause is a **netfilter/conntrack insertion race**, not "UDP is unreliable" and not CoreDNS being slow. Symptom fingerprint: latency clusters at exactly 5 s, `insert_failed` counter in `conntrack -S` increments. | Counter is the tell. |
| 5 | **Happy Eyeballs (RFC 8305).** Recommended values: Resolution Delay **50 ms** (wait briefly for AAAA after A arrives), Connection Attempt Delay **250 ms** (range min 100 ms, max 2 s); start next attempt without cancelling the earlier; interleave families, prefer IPv6. **Go's implementation is RFC 6555-style, simpler** (verified `dial.go`): `Dialer.FallbackDelay` default **300 ms**; addresses partitioned into primaries (family of the first address after RFC 6724 sort) and fallbacks; primaries tried *sequentially* (`dialSerial`), the fallback family starts after 300 ms **or immediately on primary failure**; first success wins, loser closed. No 50 ms resolution delay, no per-address 250 ms stagger within a family. `FallbackDelay<0` disables. | Go predates 8305; behaviour kept for compatibility. |
| 6 | **Dial budget split**: with a ctx deadline, `partialDeadline` gives each remaining address `timeRemaining/n` — a dead first address of 4 costs ≤ 1/4 of budget. Explains "my 30 s dial timeout fires at 7.5 s per IP". | dialSerial divides time. |
| 7 | **Idle-timeout mismatch LB ↔ app ⇒ intermittent 502/resets.** AWS ALB idle timeout default **60 s** (range 1–4000 s); NLB TCP idle **350 s** default, configurable **60–6000 s** since Sept 2024 (was fixed), UDP **120 s** fixed (AWS docs via search). ALB rule: backend keep-alive timeout **must be > ALB idle timeout**, else the target closes an idle connection at the same moment ALB sends a request on it → ALB gets FIN/RST → **502**. NLB is different: after 350 s idle the flow entry is silently removed, **no FIN**; next packet gets RST from the NLB → client sees `connection reset by peer` / hang; fixes: TCP keepalive/heartbeat < timeout, or raise timeout. nginx default `keepalive_timeout` 75 s (from memory; UNVERIFIED) > 60 ✓.; Go `http.Server` with `IdleTimeout=0` and `ReadTimeout=0` → idle conns never closed by Go (safe w.r.t. ALB). Go server `IdleTimeout` must be set **greater** than ALB's, e.g. 75–120 s. Same rule applies client→proxy→upstream at every hop (Envoy `idle_timeout`, nginx `keepalive_timeout` vs upstream `keepalive_timeout`). | The side that closes first must be the one that knows the connection is idle; a peer that closes "at the same instant" as a new request creates a race. |
| 8 | **Client-side race: retry on reused idle connection.** Go `http.Transport` reuses an idle pooled conn; if the server closed it, the write succeeds/fails ambiguously. Verified logic (`persistConn.shouldRetryRequest`, `Request.isReplayable`): retried transparently **only if the connection was reused** (never on a fresh one), AND (nothing was written [`nothingWrittenError`] and body is nil/NoBody or has `GetBody`) OR (request is replayable — method GET/HEAD/OPTIONS/TRACE, or has `Idempotency-Key`/`X-Idempotency-Key` header, body nil/NoBody/GetBody — AND error is server-closed-idle EOF before first response byte / non-EOF read error on first response byte). **POST without an Idempotency-Key is not retried** → app sees `EOF` / `connection reset by peer` / `http: server closed idle connection`. Same as go.mod-level answer: retries hide in the transport, so LB 502s often reach POSTs only. `PUT`/`DELETE` are idempotent per RFC 9110 but Go's replay list is only GET/HEAD/OPTIONS/TRACE (+header). | Go can't know a POST wasn't processed. |
| 9 | **Connection draining / graceful shutdown ordering** (k8s). On delete: control plane starts marking endpoints terminating (not instant) **and in parallel** kubelet runs `preStop` then sends SIGTERM (k8s docs, verified: default `terminationGracePeriodSeconds` = 30 s; preStop overrun gets +2 s once). Endpoint removal propagates to kube-proxies / ingress / mesh asynchronously (seconds), so if the process closes its listener at SIGTERM, requests still routed → connection refused / 502. Correct order: (a) fail readiness immediately (or rely on terminating status) → (b) **sleep** (5–15 s, preStop `sleep` or in-app timer) for propagation → (c) `http.Server.Shutdown(ctx)` (stops listeners, closes idle conns, waits for active; new responses get `Connection: close` since `doKeepAlives` false while shutting down; HTTP/2 gets GOAWAY; hijacked/WebSocket conns NOT tracked — you must close them via `RegisterOnShutdown`) → (d) exit before grace period ends; grace ≥ sleep + max request time. `terminationGracePeriodSeconds` counts preStop + shutdown together. LB-side: ALB *deregistration delay* (default 300 s), NLB similar — keeps existing flows, stops new. | Two asynchronous systems (endpoint propagation vs signal delivery). |
| 10 | **502 vs 503 vs 504 at a proxy** (RFC 9110): **502 Bad Gateway** = proxy got an invalid response or the upstream connection failed/reset/closed before a valid response (upstream crash, keep-alive race, protocol error, TLS mismatch); **503 Service Unavailable** = no healthy/available upstream, overload shedding, maintenance (often with `Retry-After`; ALB: no registered/healthy targets); **504 Gateway Timeout** = upstream accepted but didn't respond within proxy's timeout (ALB: target idle/response > idle timeout; nginx `proxy_read_timeout` 60 s). Debug direction: 502 → look at upstream closes/logs, 504 → upstream slow (check timeout ordering client < proxy < upstream), 503 → health checks/capacity. Go handler tie-in: ReverseProxy returns **502** on upstream error by default; context cancel → 502 too (`ErrorHandler`); it never emits 504 unless you map `context.DeadlineExceeded`. | Codes classify *who* failed at the proxy hop. |
| 11 | **L4 LB + long-lived conn.** After scale-out from 3→6 pods, old connections stay; skew persists until reconnect. `least_conn` at L4 only affects new conns. Also `MaxConnectionAge` causes reconnect storms if not jittered (grpc-go adds ±10 %) and needs client-side LB/DNS re-resolve: grpc-go's DNS resolver does **not** poll by TTL — it re-resolves only on `ResolveNow` (triggered by connection loss/GOAWAY), with a min 30 s interval (`MinResolutionInterval`, verified in `dns_resolver.go`). So after MaxConnectionAge, new pods are only found once a subchannel breaks + 30 s floor. | Design: resolver is event-driven. |
| 12 | **HTTP/2 in Go also pins to one connection** per host (`ForceAttemptHTTP2`, streams limit ~100 by server `MAX_CONCURRENT_STREAMS`; Go 1.26 adds `HTTP2Config.StrictMaxConcurrentRequests`, new connection once stream limit hit) — a Go HTTP/2 client behind an L4 LB has the same skew as gRPC. | Multiplexing removes the natural connection churn. |
| 13 | **X-Forwarded-For trust.** XFF is a client-controlled list, each proxy appends the peer IP; **leftmost is spoofable**. Use rightmost-untrusted: walk from the right, skipping known proxy CIDRs; take first non-trusted hop, or take a fixed count from the right if hop count known. Never use XFF for rate limiting/authz unless the edge overwrites it. Go `httputil.ReverseProxy` `Rewrite` + `SetXForwarded()`: **drops inbound XFF by default** (sets from the peer); only if you copy `r.In.Header["X-Forwarded-For"]` it appends (verified in source docs). The deprecated `Director` appended by default (1.26 notes: Director deprecated). `r.RemoteAddr` is the LB IP. | Any header is client input until a trusted proxy rewrites it. |
| 14 | **PROXY protocol** (HAProxy spec v1 text / v2 binary): a header sent by the proxy as the **first bytes** of the TCP connection carries original src/dst; works for non-HTTP and TLS passthrough (L4 LB preserves client IP without XFF). Trust issue (spec §): "allowing untrusted parties to spoof their connection addresses" — the receiver **must** only accept PROXY headers from trusted proxy addresses and must require it on that listener (not optional): a listener that *optionally* parses it can be spoofed by any client that sends a header; a listener that *expects* it and gets none must reject. Go: not in stdlib (third-party e.g. `pires/go-proxyproto` — **UNVERIFIED**, from memory); wrap `net.Listener`. AWS: NLB proxy protocol v2 toggle on target group; ALB uses XFF instead. | Pre-connection metadata has no authentication. |
| 15 | **TLS termination vs passthrough (L4)** interacts with health checks and retries: L7 can retry idempotent requests to another backend on 502/connect failure (Envoy `retry_on`, nginx `proxy_next_upstream` — nginx does NOT retry non-idempotent requests by default after sending, since 1.9.13 — from memory, **UNVERIFIED**). L4 cannot. | L7 sees requests. |
| 16 | **Anycast/GeoDNS/CDN**: not DNS TTL failover but BGP/edge; DNS answers may vary by resolver location (EDNS Client Subnet); a DNS-based blue/green cutover is slow and uncontrollable — use weighted records only for coarse traffic shifting. | Resolver ≠ client location. |

## 3. Common misconceptions
- "DNS TTL 30 s means failover in 30 s" → recursives may floor TTL, and pooled connections persist; failover is per-new-connection.
- "Go caches DNS" → Go has **no** resolver cache; each new dial resolves (cgo path caches nothing by itself either, unless nscd/systemd-resolved). "Go uses cgo DNS in Docker" → pure-Go by default.
- "ndots:5 means 5 retries" → it means names with fewer than 5 dots get search-list expansion first.
- "The 5 s DNS delay is CoreDNS being slow / UDP packet loss" → it's the conntrack insert race + retry timeout.
- "Load balancer round-robins my gRPC calls" → only if it is an L7/h2-aware balancer or the client does the LB.
- "502 means my app returned 502" → it's generated by the proxy (or ReverseProxy); app may have only closed a connection.
- "Set app keep-alive < LB idle timeout to be safe" → the reverse: app/target keep-alive must exceed the LB's.
- "Happy Eyeballs is 250 ms in Go" → Go's is 300 ms `FallbackDelay`, no resolution delay.
- "Readiness probe failing drains connections" → it only removes endpoints; existing conns stay until you close them; and deletion doesn't wait for readiness change.
- "`X-Forwarded-For` first IP is the client" → first IP is whatever the client claimed.

## 4. Go tie-ins
- `GODEBUG=netdns=go` / `cgo` / `go+2` (debug print), `Resolver{PreferGo:true, Dial: …}` to point at a specific server (used in my experiment), `Resolver.LookupNetIP`, `net.DNSError{IsNotFound,IsTimeout,IsTemporary}`.
- Go resolver internals: search-list expansion (`nameList`), `attempts` × `servers`, `timeout` 5 s default (resolv.conf `options timeout:N attempts:N` respected, container had 2/3), `single-request`/`single-request-reopen` (serialises A/AAAA), `rotate`, `use-vc`, `edns0`, resolv.conf re-read ≤ every 5 s, `/etc/hosts` cached briefly.
- `net.Dialer{FallbackDelay, Timeout, KeepAlive}`; `DialContext` deadline split across addresses; `http.Transport{IdleConnTimeout, MaxIdleConnsPerHost, MaxConnsPerHost, ForceAttemptHTTP2, DialContext}`; to bound connection lifetime you must do it yourself (no `MaxConnLifetime`) — e.g. per-request `Close: true` sampling, or `CloseIdleConnections()` on DNS change; `httptrace.GotConn{Reused,WasIdle,IdleTime}` proves reuse-race hypotheses.
- Graceful shutdown template: `signal.NotifyContext(SIGTERM)` → `readiness=false` → `time.Sleep(preStopDelay)` → `srv.Shutdown(ctx)` with timeout → `srv.Close()` fallback; `RegisterOnShutdown` for hijacked; `BaseContext` for in-flight cancellation.
- gRPC-go: `grpc.NewServer(grpc.KeepaliveParams(keepalive.ServerParameters{MaxConnectionAge, MaxConnectionAgeGrace, Time (default 2 h), Timeout (20 s)}), grpc.KeepaliveEnforcementPolicy(...))`; client `grpc.WithKeepaliveParams`, `WithDefaultServiceConfig({"loadBalancingConfig":[{"round_robin":{}}]})`, target `dns:///svc.ns.svc.cluster.local:port` (headless Service). grpc keepalive: client default disabled; server enforces min ping interval 5 min (`MIN_RECV_PING_INTERVAL_WITHOUT_DATA` 300 s) → violating ⇒ `GOAWAY ENHANCE_YOUR_CALM` (grpc core keepalive doc; verified).
- `httputil.ReverseProxy` XFF behaviour & default 502 (see #10, #13).
